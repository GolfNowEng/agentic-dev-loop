# dev-loop 2.0.0 Worker Monolith — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Merge research-loop into dev-loop and ship `dev-loop:2.0.0`: one named
worker per project that claims a ticket, runs `/ticket-refine`, and on green
runs `/ticket-to-pr` on the same ticket with no human gate, logging one record
per ticket iteration.

**Architecture:** Phase A (Tasks 1–7) is a pure migration: research-loop's
history is imported under a temp subdirectory, the 17 shared `src/` files are
unified test-first into `src/core/`, and each role's runner moves under
`src/roles/<role>/`. Behavior doesn't change, and each role stays runnable with
`--phase`. Phase B (Tasks 8–17) adds the v2 behavior: the combined config,
v2 paths, the session lockfile, the iteration record, per-role ceilings, the
blocker gate, the worker cycle, skills that receive their run directory, the
v1/v2 readers, evals, and the cutover scripts.

**Tech Stack:** Node ≥ 22.18 running `.ts` directly (type stripping),
TypeScript 7, vitest 4, `gh` CLI, Jira REST v3, and `claude -p` headless. No new
runtime dependencies.

**Spec:** `docs/superpowers/specs/2026-11-10-dev-loop-v2-design.md` (approved).
Read it alongside this plan; section numbers below (§x.y) refer to it.

## Global Constraints

- The live v1 loops stay untouched until cutover (§3, A6). All work happens in
  a worktree on `feat/v2-monolith`. The main checkout goes back to `main`
  (Task 0), because v1 `npm run loop` runs from it.
- `npm test` is green before and after every change to `src/`. The failing
  test is committed before its implementation (the RED commit), then GREEN.
- Contract strings stay byte-identical: `✅ research-loop -`,
  `❌ research-loop -`, `pipeline:research`, `pipeline:dev` (A1).
- v2 trigger label is `pipeline:v2.0.0` on `repo:webtarsthree` (§3, G6). It is
  read from config, never from `package.json`.
- `package.json` `version` is `2.0.0` and `name` is `dev-loop`. Every v2 log
  record carries `loop_version`.
- Ceilings carry over as they are today: research $50 / 120 min, dev $20 /
  75 min, and `maxRunsPerDay` 100 per role (§6.3, §6.4).
- `autoPromoteLabel` is removed, and the loader rejects any config that sets it.
- Paths: `runs/v1/{research,dev}/…` are frozen, `runs/v2/<project>.jsonl`, and
  `.pipeline/v2/<project>/<session>/<ticket>/` (§6.5).
- Banned in all code, skills and evals: `git push --force`,
  `--force-with-lease`, `--no-verify`, `-n` on commit or push, and
  `gh stack push|sync|submit` (A4, §8).
- The session suffix (`— dev-1`) goes only on text that `src/` builds, never on
  skill-posted comments (§6.2).
- Pause the worker only for a ceiling breach or a config/auth error. Every
  per-ticket failure moves on to the next ticket (§6.3).
- Escalation: if a divergence can't be classified from the code, the git log and
  the two changelogs, **stop and ask the manager**. Never guess (§6.1 (c)).
- RED commit means a commit that contains only the new or changed failing
  tests. Every task that changes `src/`, hooks or graders has one.
- "Project" in every path is the slug from `repoSlugFromUrl(config.targetRepo.url)`,
  the same value v1 uses. Today it equals the `--project` name for all three
  configs, and a test pins that.
- Untrusted identifiers are validated wherever they enter: ticket keys
  (`/^[A-Z][A-Z0-9_]+-\d+$/`), session names (`/^[a-z0-9][a-z0-9-]{0,31}$/`),
  and project slugs (`/^[a-z0-9-]+$/`). A key that fails validation is dropped
  and logged, never interpolated into JQL, a path, a prompt or a `gh` argv.
- Each spawned `claude -p` gets `--max-budget-usd <role maxCostPerRunUsd>` and
  is killed on its role's `runTimeoutMin`, SIGTERM then SIGKILL after 30 s.
  v1 enforced both only after the run ended.
- The secret-scan hooks deny on their own failure (exit 2), as the hooks do
  today. Never weaken that in a merge.

## Review Focus

1. **The search index lags behind a just-written transition.** A ticket bounced
   or handed off this iteration can still match the next poll for a few
   seconds. Expected: it is never re-run. Pinned in Task 13
   (restart-safe `recentlyEnded` exclusion test).
2. **A ticket gets stranded between phases.** This happens when research is
   green but the label swap to the dev handoff label throws, or a research
   ceiling breach skips the handoff. The ticket is then In Progress with the
   research label, and neither poll matches it. Expected: the next iteration,
   or the next start, completes the handoff from the v2 log. Spec gap,
   resolved as a builder's call: §6.3 says "resumes from where Jira says"
   but no poll matches this state. Pinned in Task 13 (`pending handoff`
   tests).
3. **A blocker link points at a ticket that has no PR, is in another project,
   or was deleted, or `gh` errors.** Expected: not cleared, the ticket is
   skipped, and the skip is logged with the blocker key. The check fails
   closed. Pinned in Task 12.
4. **A stale lockfile is left after a crash or `kill -9`.** Expected: if the
   lockfile's pid is dead, the next start reclaims the name. If the pid is
   alive, it refuses and names that session. Pinned in Task 10.
5. **The v2 worker is pointed at a project whose labels are still v1**
   (`catalog-ui-*` before cutover). It would compete with live v1 for the
   same tickets. Expected: it refuses to start in worker mode. Pinned in
   Task 8 (label-version guard).
6. **The process dies mid-phase** (`kill -9`, sleep, OOM). The ticket is In
   Progress with no iteration record. Expected: the next start finds the
   in-flight ticket recorded in the lockfile and resumes it. Research is
   re-run without a claim. Dev first checks GitHub for an open PR for the
   key, and if one exists it self-heals to Code Review instead of building
   again. Pinned in Task 10 and Task 13.
7. **A phase keeps erroring.** A deterministic crash or timeout leaves the
   ticket's label in place, so it would be re-run at full cost forever.
   Expected: after `maxAttemptsPerTicket` (2) error/killed attempts of one
   role, the ticket moves to Blocked with a `src`-built comment and is never
   picked again. Pinned in Task 13.

Mechanics:
- **One live worker per project.** First scan **every** `*.lock` in `dir`.
  Any lock whose `isAlive` returns true raises `LiveWorkerError`.
- **Stale locks.** `isAlive` checks the pid with `process.kill(pid, 0)`
  *and* checks that the process start time matches `started`, using
  `ps -o lstart= -p <pid>`, so a reused pid isn't treated as alive. A stale
  lock is reclaimed by `rename(lock, lock + ".stale-<ts>")`; only the
  process whose rename succeeds proceeds. It then creates the new lock with
  `open(path, "wx")`. On EEXIST it rescans once, then gives up with
  `LiveWorkerError`.
- **Resuming.** The returned `inFlight` is the stale lock's `inFlight`, which
  Task 13 resumes. `setInFlight` rewrites the lock through a temp file and
  rename.
